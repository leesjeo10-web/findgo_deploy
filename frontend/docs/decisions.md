# Finder 결정 기록

## 개인 Notion 정책 수정안 (2026-11-12) — 사용자 선택 반영

과거 미확정 기록을 다음 선택으로 대체한다. 공동 원본·프론트·백엔드 코드는 바꾸지 않고 개인 Notion 복사본에 반영했다. 팀 공유 전의 개인 수정안이다.

- 최종 서비스는 물품 목록·상세·검색·게시물 사진 원본 조회까지 로그인 필수다.
- 모든 학생 계정의 전화번호는 필수이며, 계정 번호를 작성자 연락처로 사용한다.
- 전화번호는 항상 삭제 금지, 수정만 허용한다. 게시물 상태에 따른 삭제 예외는 없다.
- 사진은 JPG/PNG 한 장·5MB 이하로 고정하며 다른 형식 변환은 제외한다. 추가 형식 지원 가능 여부만 후속 검토한다.
- 미연결 사진은 업로드 3시간 뒤 서버가 자동 삭제한다.
- 관리자에게 교무실 번호와 휴대전화 번호를 각각 두고 함께 표시한다. 구체적인 DB/API 필드명은 후속 설계로 남긴다.
- API 계약·디자인 심화 논의는 이번 범위에서 진행하지 않는다. 로그인 없는 로컬 프론트 범위도 유지한다.

## 현재 구현 범위 (2026-11-12) — 로그인 없이 프론트엔드 개발 시작

사용자가 디자인과 물품 기능 구현을 시작하라고 요청했다. 아래의 이전 구현 대기 지시를 이번 범위에 한해 대체한다.

- 기존 Finder에 선배님 디자인의 목록·상세·등록·수정·내 물품 화면을 구현한다.
- 로그인·회원가입·토큰 발급/저장/헤더·인증 상태·화면 보호는 구현하지 않는다. 가짜 로그인 사용자도 만들지 않는다.
- 실제 백엔드는 이후 조율한다. 이번 물품 데이터·사진은 브라우저 IndexedDB에 저장하며, 서버 API·공유 DB에 저장됐다고 설명하지 않는다.
- 계정 프로필·계정 연락처 확인·비밀번호 변경·관리자 기능은 보류한다. 연락처 필수라는 최종 기획을 폐기하지 않으며, 이번에는 계정 기반 등록 조건을 적용하지 않는다.
- 미확정 번호 삭제 제한·관리자 번호 예외·3시간 자동 삭제·새 로그인 정책은 추가하지 않는다.
- 목록·검색·필터·20개씩 더 보기·사진 선택·폼 검증·등록·수정·상태 변경·삭제·내 물품 집계를 구현한다.
- 예시 사용자·전화번호·실제 게시물처럼 보이는 초기 샘플을 넣지 않는다. 처음에는 빈 목록이며 직접 등록한 항목부터 표시한다.
- Notion·디자인 원본·백엔드는 수정하지 않는다. 커밋·푸시·배포는 하지 않는다.

## 최신 기획 재검토 (2026-11-12) — 문서만 갱신, 구현 대기

현재 개인 Notion에 새로 복사된 문서 12개와 API 표 16개를 읽고 [구조안](frontend-structure.md)을 갱신했다. 자세한 근거는 [검토 기록](spec-review-2026-11-12.md), 재사용 부품은 [19종 목록](reusable-components.md)에 있다.

### 현재 문서로 확인한 계약

- 학생은 고정된 숫자 6자리 아이디(입학년도 2자리 + 1학년 때 학번 4자리, 예: 261109), 관리자는 admin.
- 로그인 요청은 loginId, password. 응답은 accessToken과 사용자 정보(id, loginId, name, phone, role, mustChangePassword).
- 회원가입 없음. 목록·상세·검색을 포함한 모든 서비스 화면이 로그인 필요.
- 로그인 뒤에는 항상 물품 목록. 첫 로그인·관리자 초기화 뒤에는 비밀번호 변경을 먼저 완료. 로그인 전 주소 복귀는 하지 않음.
- 학생마다 다른 초기 비밀번호를 지급. 새 비밀번호 8~64자. 전화번호는 내 정보에서 추가·변경·삭제.
- 관리자 학생 목록·추가·비밀번호 초기화·삭제는 첫 버전 범위. 학생 삭제는 게시물·사진도 함께 삭제.
- 수정·상태 변경은 작성자, 삭제는 작성자 또는 관리자. 관리자는 다른 사람 글을 수정하지 않음.
- 로그아웃은 서버 요청 없이 토큰·사용자 정보를 지운 뒤 로그인 화면. 비밀번호 초기화 뒤 기존 토큰은 만료까지 유지하는 정책이 문서에 있음.

### 이번 대화에서 사용자가 추가 확정한 내용

- **사진 원본도 로그인한 사용자만 조회**한다. Notion 사진 조회 API의 인증 X는 이 결정과 다르다.
- **분실물 글 등록 시 연락처는 필수**다. 계정 연락처를 이용하는 구조로 계획하고, 다른 용도의 학생 계정 전화번호까지 항상 필수로 바꾸지는 않는다.
- **JPG/PNG만 업로드하고 다른 형식의 JPEG 변환은 제외**한다.
- **연락처 저장 위치:** 현재 기획은 마이페이지의 계정 전화번호(members.phone)를 게시물 작성자 연락처로 사용한다. 게시물마다 번호를 따로 받는 구조가 아니다. Notion의 기존 규칙은 선택 입력·삭제 가능이며, 위 분실물 등록 필수 결정은 등록 시 계정 연락처 존재 여부를 확인하는 규칙으로 해석한다.
- **번호 삭제 정책은 미확정:** 사용자는 "번호 수정은 허용하되 삭제는 막는 방식"을 제안했지만 명시적으로 확정하지 말라고 했다. 모든 계정의 삭제를 막을지, 찾는 중인 분실물 글이 있을 때만 제한할지, 기존 선택 입력 정책을 유지할지는 결정하지 않는다.
- 3시간 미연결 사진 정리가 첫 출시 필수인지, 관리자 교무실 번호를 허용할지는 추가 질문 중이다.

### 시작 조건·기록 구분

**실제 구현을 시작하라는 요청을 받으면 이 최신 절·구조안·최종 백엔드 명세를 다시 읽는다.** 지금은 Markdown만 갱신하고 JSX·CSS·API·Notion·디자인 원본을 변경하지 않는다.
아래 2026-11-11의 미정 항목 중 아이디 형식·로그인 필드·관리자 기능·전화번호 편집·로그인 필수 범위는 새 기획에서 구체화됐다. 과거 기록을 현재 미정 사항으로 읽지 않는다.
계정 수명주기·실제 서버 구현·이미지 인증 연결과 남은 질문은 별도로 확인한다.

## 이전 인증 방향 (2026-11-11) — 당시 문서 기록, 구현 대기

사용자가 변경한 인증 계획이다. 이전 문서의 이메일 로그인·사용자 직접 회원가입·학번 미사용 설명보다 이 절을 우선한다.

### 확정한 변경 방향

- 로그인 아이디는 **학번**으로 한다.
- 계정은 **학년별로 지급**하여 서비스를 이용하게 한다. 학생이 직접 회원가입하는 방식은 사용하지 않는다.
- **회원가입 기능은 구현 대상에서 제외**한다. 회원가입 화면·이동 링크·라우트·회원가입 API 연동도 제외하는 방향이다.
- 인증은 기존에 확정한 **JWT 토큰 방식**을 유지한다.
- 인증 영역은 지급된 계정의 로그인과 토큰 기반 로그인 상태 처리에 맞춰 준비한다. 이번 변경을 물품·검색·마이페이지 등 다른 서비스 기능의 취소로 해석하지 않는다.

### 지금 수행한 범위와 시작 조건

- 이번 요청은 **로컬 Markdown에 계획을 기록하는 것만** 허용한다. 아직 구현을 시작하지 않는다.
- 현재 로그인·회원가입 컴포넌트 뼈대, 실행 코드, 라우팅, API, 설정 파일은 변경하거나 삭제하지 않는다.
- 남아 있는 `SignupPage.jsx`, `SignupForm.jsx`는 이전 구조의 뼈대를 보존한 것이다. 회원가입을 구현하겠다는 뜻이 아니다.
- Notion의 개인 복사본과 공동 원본 모두 이번 변경으로 수정하지 않는다.
- **사용자가 구현을 시작하라고 요청하면 작업 전에 이 절을 다시 읽고**, 그때 최신 디자인·백엔드 명세와 대조하여 진행한다.

### 구현 전에 확인할 미정 항목

아래는 확정된 요구사항이 아니라 추가 확인이 필요한 내용이다. 지금 임의로 결정하거나 구현하지 않는다.

- 학번의 정확한 형식과 로그인 API의 요청 필드 이름. 기존 `email` 필드를 새 계약 확인 없이 그대로 사용하거나 `studentId` 같은 이름을 임의로 확정하지 않는다.
- 계정 생성·지급 담당과 지급 절차, 초기 로그인 정보와 비밀번호 정책. 관리자용 화면이 필요한지도 아직 정하지 않았다.
- 진급·전학·졸업 등으로 학번이나 이용 자격이 바뀔 때의 계정 처리와 기존 게시물 작성자 연결 유지 방법.
- 회원가입에서 받던 이름·전화번호를 지급 계정에 어떻게 등록할지, 연락처 없는 분실물 글의 연락 수단을 어떻게 보장할지.
- 비회원 목록·상세·검색 허용 범위를 유지할지, 지급 계정의 로그인을 서비스 진입 조건으로 할지. 계정 지급만으로 이 범위를 자동 변경하지 않는다.
- 로그인 성공 응답, 토큰 저장·만료·로그아웃 처리의 세부 계약. JWT 유지 외의 새로운 동작을 임의로 추가하지 않는다.

### 이전 문서와의 관계

아래의 2026-11-08 기록과 다른 기획 문서에는 회원가입·이메일 로그인·학번 미사용 설명이 남아 있다. 이는 이전 계획의 기록이며, 인증 구현 시에는 위 최신 계획을 우선한다. 구현과 문서 전체의 일괄 정합성 수정은 사용자의 시작 요청 후 진행한다.

## 학번·전화번호 입력 여부 (2026-11-08)

- 상태: 결정
- 현재 결정: 학번은 받지 않는다. 전화번호는 회원가입에서 선택 항목으로 받는다(`010-0000-0000` 형식). 입력하지 않으면 화면에 표시하지 않는다.
- 검토 이유: 학번은 기획 초기에 성급하게 추가한 항목이라 형식을 맞추는 대신 지운다.
- 후속 작업: 프론트엔드 회원가입 화면에 전화번호 칸이 아직 없다.

## 인증 방식 (2026-11-08)

- 상태: 결정
- 현재 결정: JWT 토큰 방식. 로그인은 JSON(`email`, `password`) → `accessToken`, `user`. 화면이 토큰과 사용자 정보를 저장하고, 요청에는 `Authorization: Bearer` 헤더를 넣는다. 로그아웃은 서버 요청 없이 토큰과 사용자 정보를 지운다. 만료되면 401 → 로그인 화면 → 로그인 후 원래 화면. CSRF는 쓰지 않는다.
- 남은 일: 체크리스트의 「개발 설계」 문서에 있는 세션 쿠키·CSRF·로그아웃 API 설명은 이 저장소에 없는 문서라 고치지 못했다. Notion에서 직접 고쳐야 한다.

## 첫 화면 (2026-11-08)

- 상태: 결정
- 현재 결정: 첫 화면은 홈(물품 목록)이다. 비회원도 목록·상세·검색을 쓸 수 있다. 등록·수정·삭제·마이페이지와 작성자 연락처 보기만 로그인이 필요하다. 없는 주소와 로그아웃 후에도 물품 목록으로 보낸다.
- 후속 작업: 프론트엔드 라우팅은 아직 `/`와 없는 주소, 로그아웃을 `/login`으로 보낸다.

## 목록 정렬 (2026-11-08)

- 상태: 결정
- 현재 결정: 등록 최신순(`createdAt`)으로 20개씩 보여 주고 "더 보기"로 이어 붙인다. `lostFoundAt`은 물건을 잃거나 주운 날짜로 표시만 한다. '찾는 중'을 위로 올리지 않고, 미해결 물품만 보려면 상태 필터를 쓴다.
- 검토 이유: `lostFoundAt`으로 정렬하면 최근 올린 글이 아래로 묻히고 같은 날짜 글의 순서가 흔들린다.

## 물품 종류 (2026-11-08)

- 상태: 결정
- 현재 결정: 물품 종류 선택·필터는 첫 버전에서 빼고 후속 개선으로 옮긴다. 화면, DB, API에 넣지 않는다.
- 후속 작업: 프론트엔드에 물품 종류 선택이 남아 있으면 지운다.

## 첫 버전 목표와 작성자 연락처 (2026-11-08)

- 상태: 결정
- 현재 결정: 분실자는 보관 장소에서 돌려받거나, 게시물에 표시된 작성자에게 연락해 돌려받는다. 연락처는 작성자의 전화번호이고 로그인한 사용자에게만 보인다. 비회원이 조회하면 서버가 연락처를 `null`로 보내고, 화면은 "로그인하면 작성자 연락처를 볼 수 있습니다."를 표시한다. 전화번호가 없는 작성자는 연락처를 표시하지 않는다. 채팅은 후속 기능이다.
- API: 물품 상세 응답에 `userName`, `userPhone`을 추가한다. 접근 조건은 '누구나 (연락처는 토큰 필요)'.

## 소유 확인·물건 전달·해결 완료 구분 (2026-11-08)

- 상태: 결정
- 소유 확인: 보관 장소에서 직접 확인하거나, 작성자에게 연락해 특징을 확인한다.
- 물건 전달: 보관 장소에서 받아 가거나, 작성자와 약속해서 받는다.
- 해결 완료: 게시물 작성자가 수정 화면에서 '해결 완료'로 바꾼다. 서비스는 이 상태만 저장한다.
- 담당: 프론트엔드는 작성자에게만 상태 선택을 보여 주고 '해결 완료'를 표시한다. 백엔드는 작성자인지와 상태 값을 확인한다. DB는 `items.status`만 바꾼다.

## 같은 물건의 분실물 글과 습득물 글 (2026-11-08)

- 상태: 결정
- 현재 결정: 첫 버전에서는 연결하지 않는다. 물건이 돌아간 뒤 두 글의 작성자가 각자 '해결 완료'로 바꾼다.

## 보관 장소 입력 (2026-11-08)

- 상태: 결정
- 현재 결정: 습득물은 보관 장소를 반드시 입력한다. DB는 분실물과 같은 테이블이라 NULL을 허용한다. 프론트엔드는 습득물 등록 화면에서만 입력창을 보여 주고, 백엔드는 습득물일 때만 필수로 검사한다. 분실물 상세 화면에도 보관 장소를 표시하지 않는다.
- 후속 작업: 프론트엔드 등록 폼은 아직 습득물의 보관 장소를 선택 항목으로 받는다.

## 사진과 물품의 연결·삭제 (2026-11-08)

- 상태: 결정
- 연결: 사진을 먼저 올려 `imageUrl`을 받고, 물품 등록·수정 때 `items.image_url`에 저장한다.
- 기록: `item_image`는 `filename`, `user_id`만 저장하고, 본인이 올린 사진인지 확인하는 데 쓴다. `item_id`는 없앤다.
- 삭제: 물품을 삭제하거나 사진을 바꾸면 예전 사진 파일도 함께 지운다. 글에 연결되지 않은 사진은 3시간 뒤 자동으로 지운다.
- 남은 일: 3시간을 세려면 업로드 시각이 필요하다. `item_image`에 업로드 시각 칸을 둘지, 파일 시각을 쓸지 백엔드에서 정한다.
- 그림: `docs/images/erd.png`(dbdiagram 코드는 `erd.dbml`)와 `docs/images/architecture.png`를 이 결정에 맞춰 다시 그렸다. Notion의 두 그림을 이 파일로 바꾼다.

## 이용 범위·공개 정보 (2026-11-08)

- 상태: 결정
- 가입 대상: 첫 버전은 학생인지 확인하지 않고 누구나 가입한다. 실제 학교에서 운영할 때 학교 이메일 제한이나 이메일 인증을 검토한다는 한계를 문서에 적는다.
- 공개 정보: 게시물 내용은 작성자가 자유롭게 쓴다. 작성자 연락처는 로그인한 사용자에게만 보인다.

## 화면 표시 공통 규칙 (2026-11-08)

- 상태: 결정
- 값이 없는 선택 항목(보관 장소, 전화번호, 작성자 연락처)은 칸 자체를 표시하지 않는다. 사진만 예외로, 없으면 기본 이미지를 보여 준다.
- 비회원에게는 연락처 자리에 "로그인하면 작성자 연락처를 볼 수 있습니다."를 보여 준다.
