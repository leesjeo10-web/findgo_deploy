# 찾Go 최신 기획·디자인·구조 재검토

2026-11-12에 조회한 개인 복사본 기준이다. 새로 들어온 문서의 ID가 이전 복사본과 달라, 예전 페이지 대신 현재 루트 아래의 새 페이지를 읽었다.
Notion 원본·개인 복사본·초기 체크리스트는 수정하지 않았고, 초기 체크리스트는 조회 대상에서도 제외했다.
현재 결과는 구조 계획과 문서 검토다. UI·API 구현이나 실제 백엔드 검증 결과가 아니다.

## 판단과 구조 영향

app / features / shared 틀은 유지할 수 있다. 다만 이전 구조안만으로 새 기획 전체를 충족하지는 못한다.

| 새 기획 | 구조 반영 |
| --- | --- |
| 첫 로그인·초기화 후 강제 비밀번호 변경 | auth에 PasswordChangePage·PasswordChangeForm. 페이지 추가는 제안, 폼은 일반 변경과 공유 |
| 모든 화면 로그인 필요 | RequireAuth 범위 확대. 비회원 목록·상세·검색·연락처 안내 상태 제외 |
| 학생 추가·초기화·삭제 | features/admin 추가 제안. 관리자 디자인은 아직 없음 |
| 관리자 역할 | RequireAdmin과 Header 관리 메뉴. 게시물 삭제는 기존 상세·삭제 흐름 활용 |
| 내 정보 수정 | MyProfile 연락처 편집 + auth의 PasswordChangeForm. 별도 회원가입이나 프로필 중복 저장 없음 |
| 사진 원본 로그인 필수 | ItemImage로 사진 표시를 공유하고, 보호된 조회 방식은 실제 API와 맞춤 |
| 분실물 연락처 필수 | 등록·수정 폼에서 계정 연락처 확인. 없는 경우 입력 경로 안내, 서버 최종 검사 필요 |

전체 트리: [frontend-structure.md](frontend-structure.md). 재사용 후보 **19종**: [reusable-components.md](reusable-components.md).

## 이번 대화에서 사용자가 확정한 내용

1. 사진 원본도 로그인한 사용자만 본다. API 표의 사진 조회 인증 X와 다른 결정이다.
2. 분실물 글을 등록할 때 연락처를 필수로 받는다. 학생 계정 전화번호가 항상 필수라는 뜻은 아니다.
3. 첫 버전 업로드는 JPG/PNG만 허용하고 다른 형식의 변환은 제외한다.

위 결정은 로컬 계획에만 반영했다. Notion·백엔드·디자인 파일에는 아직 적용하지 않았다.

## 디자인에서 조정할 부분

| 위치 | 현재 디자인 | 새 기준·검토 결과 |
| --- | --- | --- |
| 로그인·메인·상세 | 로그인 없이 둘러보기, 비회원 배너·연락처 잠금 상태 | 서비스 화면은 전부 로그인 필요. 해당 진입·문구 제외 |
| 로그인·마이페이지 | 20260137 같은 8자리 예시, 숫자 전용 입력 안내 | 학생 6자리 예시로 조정. 로그인에는 admin도 들어가므로 숫자 6자리 검사·숫자 키패드 강제 금지 |
| 첫 비밀번호 변경 | 현재 비밀번호 칸 숨김, 초기 비밀번호가 모두 같다는 안내 | 문서는 현재 비밀번호를 요구하고 학생별 다른 초기 비밀번호 지급. 같은 3칸 폼 사용 제안 |
| 로그인 완료·로그아웃 | 마이페이지나 이전 화면·물품 목록으로 이동하는 시연 | 로그인 완료는 목록(필요시 변경 먼저), 로그아웃은 로그인 화면 |
| 관리자 | role·관리 메뉴·학생 관리 시안 없음 | 학생 화면 디자인을 바탕으로 영역·역할만 계획. 실제 디자인은 후속 확인 |
| 로그인 실패 | 5회 실패·10분 잠금, 현재/초기 비밀번호 재사용 금지 | 최신 API·입력 규칙에 계약 없음. 자동 확정하지 않고 백엔드 합의 후 반영 |
| 상세 | guest/member/owner만 구분 | admin의 남의 글 삭제와 본인 글 권한을 별도 처리 |

등록 HTML의 maxlength는 이름·장소 120, 설명 2100이지만 별도 검사는 각각 100·2000을 사용한다. 단순히 시안 숫자를 복사하지 않고 명세 제한과 초과 입력 안내 방식을 함께 맞춘다.
이전 비회원 연락처 분기 문제는 현재 출시 범위에서 비회원 상세가 제외되어 우선 적용 대상이 아니다.

## 아직 남은 충돌·추가 확인

### 연락처 위치 설명과 미확정 의견

- 전화번호는 마이페이지에서 계정 정보(members.phone)로 저장하고 물품 상세의 userPhone으로 표시한다. 게시물별 전화번호 입력·저장 필드는 현재 기획에 없다.
- 기존 Notion은 계정 번호를 선택 입력·삭제 가능으로 정한다. 이번 분실물 등록 연락처 필수 결정은 등록할 때 계정에 번호가 있는지 확인하는 규칙이며, 모든 학생 계정의 번호가 처음부터 필수라는 뜻으로 확대하지 않는다.
- 사용자는 "번호 수정은 가능하지만 삭제는 못 하게 하는 방식"을 제안했으나 **확정하지 말라고 명시**했다. 전체 삭제 금지인지, 찾는 중인 분실물 글이 있을 때만 제한할지 등은 미정이다. 삭제 제한을 구현하거나 확정 정책으로 기재하지 않는다.
- FOUND→LOST 수정도 연락처 확인이 필요하다. 분실물 등록 뒤 번호를 지울 수 있게 둘지의 문제는 별도 결정으로 남긴다.

### 사용자 답변을 기다리는 정책

- **사진 3시간 정리:** 개요·기능·ERD에서는 동작 규칙이고 테스트에는 출시 후 수정 가능으로 남아 있다. 첫 버전 필수/후속 여부를 질문 중이다.
- **관리자 교무실 번호:** 교무실 번호 권장과 전체 010 형식 제한이 충돌한다. 관리자 예외 여부를 질문 중이다.

### 구조를 유지하면서 보완할 계약·검증

| 항목 | 확인한 내용 | 제안·남은 일 |
| --- | --- | --- |
| 첫 변경 전 서버 제한 | 화면 이동 규칙은 구체적이지만 API 표에 제한 대상·오류 구분이 없음 | 변경 전 허용할 API와 서버 오류 코드를 합의. 화면 숨김만으로 끝내지 않음 |
| 비밀번호 변경 성공 | API는 204로 사용자 정보를 안 줌 | GET /api/auth/me 재조회로 mustChangePassword 갱신하는 방식 제안 |
| 관리자 본인 게시물 | 일반 기능도 가능하지만 일부 문구는 ADMIN이면 삭제만 표시 | 작성자면 수정, 작성자 또는 관리자면 삭제로 권한을 나눌지 명확화 |
| 등록 응답 유실·재시도 | 테스트는 중복 저장이 없어야 한다고 요구하나, 흐름은 마이페이지에서 수동 확인하도록만 안내 | 버튼 잠금과 구별. 서버에서 같은 등록 시도를 식별할 계약을 합의하거나 테스트 보장 범위를 조정 |
| 재시도 테스트 방법 | 시나리오 6은 백엔드를 중지해 놓고 요청 | 저장은 성공했으나 응답만 유실된 상황을 별도로 재현해야 중복 방지를 검증할 수 있음 |
| 마이페이지 개수 | totalElements 응답은 있으나 구분별 전체 개수 전용 응답은 없음 | 현재 페이지 content.length 사용 금지. type별 조회의 totalElements 재사용 방식 등 실제 API와 확인 |
| 학생 검색 | 문서에는 아이디·이름 검색, API는 검색 조건 없는 전체 배열 | 초기에는 받은 목록에서 화면 필터 제안. 서버 검색으로 바꾸면 계약 추가 |
| 학생 추가 전화번호 | 개요는 선택 입력을 언급하지만 학생 추가 API에는 phone이 없음 | 관리자 폼에서 받을지, 학생이 첫 로그인 후 직접 추가할지 통일 필요 |
| API 오류 본문 | HTTP 상태와 안내 의미는 있지만 공통 오류 객체·필드별 오류 예시는 없음 | 칸별 오류를 표시할 code/message/fieldErrors 등의 실제 형식 확인. 여기서 필드명을 확정하지 않음 |
| 테스트 범위 | 최신 시나리오는 주로 습득물 등록 7개이며 이전 검토의 확장안은 새 복사본에 없음 | 로그인·첫 변경·전화번호·LOST 연락처·관리자·계정 삭제·사진 보호·검색·20건 초과 집계 테스트 추가 필요 |

비밀번호 초기화 뒤 이미 발급된 토큰은 만료까지 유효하다는 정책은 예외 문서에 명시돼 있다. 이를 즉시 전체 기기 로그아웃으로 설명하지 않는다.
계정 삭제 뒤 기존 토큰의 처리, 토큰 만료 시간·저장 방식과 이미지 인증 연결은 실제 백엔드와 확인해야 한다.

## 수행 범위

- 구조·라우터·기능별 README와 결정 기록만 갱신했다. 이전 기획 원문 9개는 통째로 덮어쓰지 않고 과거 스냅샷임을 문서 목록에 표시한다.
- 기존 JSX 뼈대·실행 코드·CSS·설정·디자인 자산을 보존한다. Notion은 조회만 했다.
- 실제 브라우저 표시·API 통신·DB 동작·보안 테스트·배포 검증은 하지 않았다.
